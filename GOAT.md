# GOAT — Point central du projet

> Ce fichier est le point d'entrée du projet GOAT : il décrit le projet dans son ensemble et relie les fichiers de contexte détaillés. C'est lui qu'on met à jour et qu'on relit en premier avant de continuer le travail.

## Le projet

- **GOAT** : application mobile de gamification du ski (RunCards, marché de pistes).
- Portée par l'association **NEEV** (think tank "nouveaux usages numériques dans le sport"), co-fondée par **Eliott** et **Yannick Devin**.
- Répartition des rôles : Eliott = encadrement technique et architecture logicielle ; Yannick = stratégie produit / UX.
- GOAT est candidat à un partenariat avec l'école **EPITA** (PFEE) pour le développement technique de l'application.

### Architecture

Package Swift `GOATKit` à la racine + coque d'app iOS :

| Chemin | Rôle |
|---|---|
| `Sources/GOATCore` | Modèles de la spec, règles métier (statut de session, visibilité, blocage, génération d'Echos), geohash, protocole `PresenceBackend`, `InMemoryBackend` + données de démo. Aucune dépendance UI. |
| `Sources/GOATUI` | Écrans SwiftUI, `AppState` (état partagé), `LocationProvider` (CoreLocation), stockage local du profil. |
| `App/GOATApp.swift`, `project.yml` | Coque iOS (XcodeGen) qui embarque `GOATUI`. |
| `Tests/GOATCoreTests` | 37 tests (Swift Testing) sur les règles de la spec. |
| `web/src/core` | Portage TypeScript de `GOATCore` (mêmes modèles, règles, contrat `PresenceBackend`, backend en mémoire, démo). |
| `web/src/state`, `web/src/ui` | État applicatif (`AppState`, géolocalisation du navigateur, stockage local) et écrans React. |
| `web/src/auth` | Comptes : contrat `AuthService` / `ProfileRepository`, implémentation Supabase (email + mot de passe, et Google), implémentation en mémoire (tests et `?auth=memory` / `?auth=memory-google` en dev), garde-fou sur les clés. |
| `web/public` | Manifeste PWA, service worker, icônes. |
| `web/tests` | 139 tests (Vitest) : règles métier (mêmes scénarios que Swift), comptes, adaptateur Supabase, et `tests/sql` (migrations appliquées sur un vrai Postgres, PGlite). |
| `supabase/` | Migrations SQL (comptes : tables, sécurité RLS, déclencheur d'inscription, fonctions ; prénom des comptes Google ; âge, style de sportif et catalogue de sports) et guide de mise en place, y compris de Google. |

Les deux versions partagent la même logique **écrite deux fois** (Swift et TypeScript), gardée alignée par des tests équivalents. À terme, avec un vrai backend, ces règles (visibilité, blocage, Echos) devront vivre côté serveur, ce qui supprimera cette duplication.

### Lancer et tester

- **App** : `brew install xcodegen && xcodegen generate && open GOAT.xcodeproj`, puis Run sur un simulateur iPhone (iOS 17+). Sans XcodeGen : créer un projet iOS App dans Xcode, ajouter ce dossier comme package local, copier `App/GOATApp.swift`, et déclarer `NSLocationWhenInUseUsageDescription` (texte dans `project.yml`). Sur simulateur, régler une position via *Features → Location*.
- **Tests** : `scripts/test.sh` (fonctionne avec ou sans Xcode). Compilation seule : `swift build`.
- **Démo** : au lancement, ~120 utilisateurs simulés bougent sur la France (sessions qui démarrent/s'arrêtent), 2 demandes d'Alliance de bienvenue arrivent, et les utilisateurs simulés acceptent tes demandes après ~4 s. En build Debug (Swift) ou dans la version web, *Profil → Outils de démo* ajoute un historique fictif pour faire apparaître des Echos ; la version web permet aussi d'imposer une position simulée (utile sans GPS).
- **Web, en local** (Node 20+) : `cd web && npm install`, puis `npm run dev` (http://localhost:5173, et l'adresse « Network » affichée pour tester depuis un téléphone sur le même Wi-Fi). `npm test` (Vitest), `npm run build` (typecheck + build dans `web/dist`, prévisualisable avec `npm run preview`).
- **Web, sur un téléphone** : la géolocalisation et l'installation exigent **HTTPS** ; en HTTP local, tout marche sauf le GPS réel (utiliser la position simulée). Ouvrir **https://goat-web-gold.vercel.app** dans Safari (iPhone) ou Chrome (Android), puis *Partager → Sur l'écran d'accueil* (iPhone) ou *Installer l'application* (Android).

### Décisions techniques (v0.1)

- **Backend derrière un protocole** (`PresenceBackend`) : Supabase est retenu pour les comptes (voir ci-dessous) et le sera très probablement pour la présence live (Realtime, à confirmer) ; brancher le backend réel = écrire une classe conforme, sans toucher aux vues. L'implémentation doit garantir : arrondi de position côté serveur, rien d'un utilisateur bloqué (dans les deux sens), Alliance = demande + acceptation par le destinataire.
- **Position** : geohash de précision 7 (~150 m) ; seul le geohash est stocké/diffusé, le pin est dessiné au centre de la cellule. Jamais de coordonnée exacte chez les autres.
- **Batterie** : CoreLocation en précision 100 m, premier plan uniquement, envoi toutes les 12 s, coupure automatique à la fin de la dernière session.
- **Carte** : MapKit `hybrid` avec relief réaliste, caméra d'ouverture 4 400 km / 45° (toute la métropole, Corse comprise, en portrait), bornée à la France. Une inclinaison plus forte est refusée par MapKit à cette altitude.
- **Carte web** : MapLibre GL JS 6, fond vectoriel OpenStreetMap servi par OpenFreeMap et relief AWS Terrain Tiles — des services tiers gratuits, sans clé d'API, **à remplacer par un fournisseur sous contrat (MapTiler, Stadia…) avant une vraie mise en production**. MapLibre 6 déduit l'URL de son worker de son propre module : avec un bundler il faut la lui fournir explicitement (`setWorkerUrl`, voir `MapView.tsx`), sinon les couches vectorielles ne s'affichent jamais.
- **PWA** : manifeste + service worker qui précharge la coquille (l'app démarre hors connexion, mais le fond de carte demande du réseau). Position : `watchPosition` en précision réduite, uniquement pendant une session et au premier plan, envoi toutes les 12 s — mêmes règles que côté iOS.
- **Comptes : Supabase** (Postgres + Auth) plutôt que Firebase : les règles de visibilité et de blocage doivent être imposées côté serveur (RLS), et Realtime servira à la présence. Email + mot de passe pour le MVP (Sign in with Apple deviendra obligatoire sur l'App Store si on ajoute d'autres connexions sociales).
- **Sécurité des comptes** : RLS partout, chaque utilisateur ne lit/modifie que son profil ; privilèges par colonne (l'ancienneté n'est pas modifiable) ; fonctions sensibles réservées aux utilisateurs connectés ; suppression du compte en cascade (RGPD). Seule la clé **publique** (anon/publishable) va dans l'app : l'app et le build refusent une clé `service_role`/secrète.
- **Sans Supabase configuré, l'app reste en mode démo local** (c'était celui du site en ligne jusqu'au 2026-09-21) : la bascule se fait uniquement par les variables `VITE_SUPABASE_URL` et `VITE_SUPABASE_ANON_KEY`.
- **Plusieurs sessions simultanées** possibles (une par sport) ; un seul pin par utilisateur.
- **Inscription en étapes** (`AuthScreen` + `ProfileWizard`) : le SDK Supabase annonce la connexion dès que le compte est créé ; `AppState.signUp` bloque donc l'ouverture de l'app (`creatingAccount`) jusqu'à ce que le profil complet soit enregistré (`save_my_profile`). Si l'enregistrement échoue après la création, la personne retombe sur l'onboarding avec un message. Un profil est « complet » avec prénom, âge, style et au moins un sport ; sinon (première connexion Google, ancien compte), il repasse par l'assistant.
- **Âge** : minimum **16 ans** (choix de Claude, à valider avec NEEV / le juridique ; la base accepte 13-120), jamais montré aux autres. Saisi comme un âge : il ne se met pas à jour tout seul avec les années (passer à une date de naissance si on veut un jour l'afficher).
- **Google** : `signInWithOAuth` avec `redirectTo` = l'origine du site (à autoriser dans *Redirect URLs* de Supabase) ; le prénom vient de `given_name` / `full_name` via le déclencheur SQL ; un même email lie automatiquement les comptes (une inscription par mot de passe jamais confirmée est supprimée à la liaison). Le bouton n'apparaît que si `VITE_AUTH_PROVIDERS` le liste.
- **Filtre de la carte** : ne propose plus tout le catalogue, seulement les sports présents sur la carte et les miens.
- **Interprétations de la spec à confirmer** : visibilité « mes sports » = seuls les pratiquants du sport de la session me voient ; Echo = même sport + au moins 2 jours distincts dans la même zone (~5 km) sur 60 jours ; un profil réglé sur « mes Alliances » n'est jamais suggéré en Echo ; tribus ouvertes à tous ; `tribu_id` de la spec omis sur `Alliance` (`Tribu.memberIDs` suffit).

### Limites connues / prochaines étapes

- Premier build iOS à valider dans Xcode (`project.yml` non testé, aucun binaire XcodeGen sur la machine).
- Auth réelle (Sign in with Apple / Supabase Auth) : le compte est local pour l'instant (profil en JSON dans Application Support).
- Session « fantôme » si l'app est tuée en pleine session : il faudra un heartbeat/expiration côté serveur.
- Pas de clustering des pins (seulement une réduction de taille selon le zoom).
- Photo de profil stockée en local (JPEG 400 px) ; upload à prévoir avec le backend.
- Signalements enregistrés mais sans back-office de modération.
- **Inscription réelle pas encore essayée depuis l'app** : la base du projet Supabase a été vérifiée (schéma identique à la migration, test de fumée SQL annulé 23/23 sur le vrai moteur), mais l'adaptateur web n'a jamais parlé au vrai service Auth (il n'est testé que contre des réponses HTTP simulées). Le premier vrai test sera l'inscription depuis l'app (branchée en local et en production depuis le 2026-09-21) ; aucun compte n'existe encore.
- **Emails Supabase** : le service par défaut n'écrit qu'aux membres de l'équipe du projet et très peu par heure. Il faut soit désactiver « Confirm email » (MVP), soit configurer un SMTP (Resend, Brevo…) avant d'ouvrir les inscriptions. Idem pour « mot de passe oublié ». **« Confirm email » a été désactivé le 2026-09-21** (vérifié : `mailer_autoconfirm: true`), donc l'inscription n'envoie plus d'email ; « mot de passe oublié » garde la limite du service par défaut : SMTP à configurer avant d'ouvrir les inscriptions.
- **Légal avant ouverture au public** : conditions d'utilisation et politique de confidentialité (données personnelles + localisation, RGPD) à rédiger avec NEEV ; l'inscription affiche seulement une mention courte.
- **Comptes côté SwiftUI non faits** (l'app iOS ne compile pas encore chez toi) : même contrat prévu via `supabase-swift`. Le catalogue de sports y est aligné, mais le modèle `User` n'a ni âge ni style, et la liste des sports n'a pas de recherche (une centaine de sports à faire défiler).
- **Avec « Confirm email » réactivé** (quand un SMTP sera configuré), le profil saisi pendant l'inscription n'est pas transmis (pas de session avant la confirmation) : la personne repasse par l'assistant à sa première connexion. Amélioration possible : passer âge / style / sports dans les métadonnées d'inscription et les lire dans le déclencheur SQL.
- **Apple** : « Sign in with Apple » plus tard (compte Apple Developer payant, secret à renouveler tous les 6 mois, prénom non transmis : l'assistant le demande déjà). Il deviendra obligatoire dans l'app iOS dès qu'elle propose Google.
- Le badge de style n'est visible que sur son propre profil (les profils des autres ne sont pas encore lisibles côté serveur).
- Photo de profil stockée dans la base (data URL réduite) : à migrer vers Supabase Storage quand les profils des autres seront lisibles.
- Les « Outils de démo » restent visibles avec un compte réel tant que la présence est simulée.
- Web : non testée sur un vrai iPhone/Android (Safari iOS peut redemander l'autorisation de localisation à chaque ouverture d'une app installée ; pas de notifications ni de tâche de fond, ce que le MVP n'exige pas).
- Web : le backend étant dans la page, **deux téléphones ne se voient pas** : la « présence live » est simulée tant que le vrai backend (Supabase/Firebase) n'est pas branché.
- **Le dépôt est dans un dossier synchronisé par iCloud (Bureau)** : les dossiers de compilation/dépendances (`.build`, `web/node_modules`) y sont fragiles — iCloud a déjà créé des copies de conflit parasites (`… 2`) et fait échouer l'astuce `.nosync` pour `.build`. `web/node_modules` porte l'attribut d'exclusion iCloud (meilleur effort, non vérifiable ici). Le plus sûr : déplacer le projet hors d'iCloud (ex. `~/Developer/GOAT`).
- Hors scope MVP : RunCards/NEEV, classements, stories, montre (COROS en V2).
